# 賽程資料交換規格

**收件者**：「棋賽賽程操作台」（`qisai-schedule-web`）維護者
**提出者**：中華職業圍棋協會官網
**版本**：1.0（2026-10-02）

這份文件是自足的，不需要先看過官網的程式碼。讀完之後你應該能判斷
「這件事值不值得做」以及「做起來要花多久」。結論先講：**大概是半天的工作量，
而且不需要動到操作台現有的任何畫面或流程。**

---

## 一、兩邊各是什麼

### 你們這邊：棋賽賽程操作台

- GitHub Pages + Firebase / Firestore
- 賽務人員在上面編排對陣、記錄勝負、產生對陣表
- 已經有「產生對陣文字（給官網用）」的功能

最後一點是這份文件的前提：**這些資料你們本來就有**，目前只是靠人工複製貼上
傳到官網。我們想要的是把同一份東西多輸出一個機器讀得懂的格式。

### 我們這邊：中華職業圍棋協會官網

- 靜態網站（Cloudflare Workers），**沒有自己的資料庫**
- 每天台灣時間 20:17，GitHub Actions 跑一次抓取，把結果寫成 JSON 檔案，
  隨網站一起發布。網頁在瀏覽器端只是讀自己的靜態檔
- 棋士登入後的「棋士專區」有一頁「我的賽程」，只顯示他本人**接下來還要下**的對局

「沒有資料庫、一天抓一次」這個限制決定了下面的做法：我們要的是一個
**固定網址、公開可讀、一次抓完**的檔案，不是 API、不是即時同步。

## 二、官網現在怎麼拿資料，以及它的問題

目前是去解析海峰棋院網站上「抽籤結果公告」的純文字。原文長這樣：

```
9/22(二)10:00資格賽對陣：
徐銘均初段 vs 林聖弈三段
9/29(二)10:00初賽(左半區)1回對陣：(上、下午各一局)
林彥丞五段 vs (黃柏人初段 vs 柯沛辰初段)勝者
```

姓名後面黏著段位或頭銜（「盧奕銓新人王」），所以是拿棋士名錄做最長前綴比對
切出來的。目前跑出 **162 組對局、涵蓋 79 位棋士**，能用。

但有三個死角：

1. **對陣表做成圖片的公告** —— 完全讀不到
2. **那一輪沒有貼對陣文字** —— 讀不到
3. **公告貼出後有異動**（改期、換場地、棄權遞補）—— 官網不會知道，
   會一直顯示過期的資訊

第 3 點最嚴重。**棋士會依照這份資料安排當天行程**，顯示錯誤的日期或對手，
比什麼都不顯示更糟。而操作台是這份資料的上游，異動一定先反映在你們那裡。

## 三、所以，想請你做的事

一句話：

> **把操作台已經有的賽程，另外輸出一份固定網址、公開可讀的 JSON。**

官網拿到之後，會把「你們的資料」和「公告解析出來的資料」**交叉比對**：

| 情況 | 官網的行為 |
| --- | --- |
| 兩邊都有，而且一致 | 正常顯示 |
| 只有操作台有 | 顯示，標示資料來源 |
| 只有公告有 | 顯示，標示資料來源 |
| 兩邊**對手或日期不一致** | **整組不顯示**，並在協會後台列出差異請人確認 |

最後一列是整件事的重點。不一致時我們選擇不顯示，而不是賭其中一邊是對的。

注意「某一邊沒資料」**不算衝突** —— 公告沒貼、或操作台還沒輸入，都是常態。
只有兩邊都有同一位棋士、同一天的對局，而對手不同，才算衝突。

這段比對邏輯官網已經寫好並測過了（`scripts/scrape_pairings.py` 的 `merge()`），
你這邊不需要處理任何比對。

## 四、要什麼資料

### 範例

```json
{
  "updated": "2026-10-02T14:30:00+08:00",
  "pairings": [
    {
      "event": "第20屆棋王賽",
      "round": "資格賽",
      "date": "2026-09-22",
      "time": "10:00",
      "players": ["徐銘均", "林聖弈"],
      "winner": "林聖弈"
    },
    {
      "event": "第20屆棋王賽",
      "round": "初賽1回",
      "date": "2026-09-29",
      "time": "10:00",
      "players": ["林彥丞", null]
    }
  ]
}
```

### 欄位

| 欄位 | 必填 | 型別 | 說明 |
| --- | --- | --- | --- |
| `updated` |  | string | 這份檔案產生的時間，ISO 8601。純粹給人看的，官網不依賴它 |
| `pairings` | ✓ | array | 對局陣列。順序不拘，官網會自己排 |
| `pairings[].event` | ✓ | string | 賽事名稱。**沿用操作台現有的名稱即可**，不需要配合官網用字 |
| `pairings[].round` | ✓ | string | 輪次，例如「資格賽」「初賽1回」「本賽二回戰」。自由文字 |
| `pairings[].date` | ✓ | string | 對局日期，`YYYY-MM-DD`。**一定要有年份** |
| `pairings[].time` |  | string | 開賽時間，`HH:MM`（24 小時制）。不確定時留空或省略，官網會套慣例 |
| `pairings[].players` | ✓ | array | 長度固定為 2 的陣列，兩位棋士的**姓名**。對手尚未產生時填 `null` |
| `pairings[].winner` |  | string | 已下完的對局填勝方姓名；未下完省略或填 `null` |

### 邊界情況

| 情況 | 怎麼填 |
| --- | --- |
| 對手還沒產生（等上一輪結果） | `"players": ["林彥丞", null]` |
| 輪空 | `"players": ["林彥丞", null]`，`round` 寫「輪空」 |
| 對局已下完 | 照填，另外帶 `winner`。官網不會顯示過去的對局，但比對時用得到 |
| 棄權 / 未到 | 當成已下完，`winner` 填對手 |
| 同一天同一人有兩局（上下午） | 當成兩筆，用 `time` 區分 |
| 日期未定 | **整筆不要輸出**。`date` 是必填，沒有日期的對局官網無法使用 |

## 五、兩個最容易出錯的地方

### 1. 姓名不要帶段位或頭銜

官網是用**姓名**跟棋士名錄對應的。操作台內部若存「賴均輔 碁聖」或
「徐銘均初段」，輸出時請只給「賴均輔」「徐銘均」。

你可以拿這份清單自行驗證（公開可讀，139 位現役職業棋士）：

```
https://cpga-website.progotw.workers.dev/assets/data/players.json
```

結構是 `{ "players": [ { "id": "...", "name": "周俊勳", "rank": "九段" }, ... ] }`，
比對 `name` 欄位即可。輸出前跑一次檢查、把對不上的名字印出來，
可以省掉之後很多來回。

### 2. 日期一定要有年份，而且是台灣時間

公告只寫「9/22」，官網得自己推年份，跨年時容易出錯。
請直接給 `2026-09-22`。時間一律視為台灣時間（UTC+8），不要轉成 UTC。

## 六、實作方式（三選一）

### 方案 A：寫成 GitHub Pages 的靜態檔（**建議**）

在「封存／發布」的流程裡，額外把目前賽程寫成一份 JSON，
放進同一個 repo，網址固定：

```
https://milu891212-milu.github.io/qisai-schedule-web/public/pairings.json
```

最單純，不必管理憑證，也不會有權限問題。只要人工發布一次，官網隔天就會抓到。

### 方案 B：Firestore 另開一個公開集合

例如 `public_pairings`，安全規則：

```
match /public_pairings/{doc} {
  allow read: if true;
  allow write: if request.auth != null;
}
```

**注意**：只開這個新集合，現有集合的規則不要動。這個集合裡只放上面那些欄位，
不要有任何個資。

### 方案 C：給官網一組唯讀憑證

若不想公開，可另建一組唯讀的服務帳號。憑證由協會保管、貼進 GitHub Secrets，
不會出現在任何網頁原始碼裡。

> **請優先考慮 A。** 這份資料本來就是要公開給棋士看的對陣表，
> 沒有保密需求，而憑證要人管理、會過期、出事時難查。

## 七、技術細節

- **不需要處理 CORS。** 官網是在 GitHub Actions 的伺服器端用 Python 抓取，
  不是瀏覽器。（GitHub Pages 本來也就帶 `Access-Control-Allow-Origin: *`）
- **不需要驗證。** 方案 A / B 的網址要能直接 `curl` 到，不帶任何 header
- **編碼 UTF-8**，不要 BOM
- **網址要固定。** 不要帶日期或版本號，官網那邊是寫死一個網址的
- **檔案大小**：一整年的賽事大約幾百 KB，不需要分頁

## 八、怎麼驗收

做好之後，跑這行確認（請用無痕視窗或 `curl`，確保不是靠你自己的登入狀態讀到的）：

```bash
curl -s https://milu891212-milu.github.io/qisai-schedule-web/public/pairings.json | head -40
```

檢查清單：

- [ ] 不登入也讀得到
- [ ] 是合法 JSON（`curl … | python -m json.tool` 不報錯）
- [ ] `pairings` 不是空陣列
- [ ] 每筆都有 `event`、`round`、`date`、`players`
- [ ] `date` 全部是 `YYYY-MM-DD` 且含年份
- [ ] `players` 裡的姓名**沒有**段位或頭銜
- [ ] 姓名都能在 `players.json` 的 `name` 裡找到（對不上的請列出來討論）

把網址給協會秘書處就好，官網這邊設一個環境變數就會開始抓，程式已經寫好了。

## 九、不需要做的事

為了避免把這件事想得太大，以下明確都**不需要**：

- ❌ 不需要即時同步。官網一天抓一次，有需要時協會也可以手動觸發
- ❌ 不需要改動操作台現有的任何畫面、流程或資料結構
- ❌ 不需要提供選手聯絡方式、身分證字號、生日或任何個資
- ❌ 不需要提供歷史資料。當年度進行中的賽事就夠了
- ❌ 不需要為官網特別調整賽事名稱或輪次的寫法
- ❌ 不需要做比對、去重或錯誤處理 —— 那些在官網這邊
